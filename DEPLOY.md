# Deploying Cairn

Cairn is a single Go binary that embeds its templates, static assets and SQL
migrations. It listens on `$PORT` (Render sets this) and serves plain HTTP;
Render terminates TLS in front of it.

## How a change reaches production

```
edit locally  →  go build ./... && go test ./...  →  git push
                                                        │
                                              PR + GitHub Actions CI
                                                        │
                                            merge to main  →  Render auto-deploys
                                                        │
                                              open the URL, check /healthz
```

`main` is the deploy branch. Every push to it triggers a Render deploy (build the
Docker image, health-check `GET /healthz`, swap traffic).

## First-time Render setup (Blueprint)

1. In Render: **New → Blueprint**, point it at `RicksTC22/TaskManager`, branch
   `main`. Render reads [`render.yaml`](render.yaml) and creates the `cairn` web
   service.
2. Set these in the service's **Environment** tab (the blueprint seeds most of
   them; you still choose the value of the starred ones):
   | Var | Value | Why |
   |---|---|---|
   | `CAIRN_SECRET` | *auto-generated by Render* | signs CSRF tokens; **must stay stable** or everyone is logged out on each deploy |
   | `CAIRN_SECURE_COOKIES` | `1` | Render is HTTPS-only |
   | `CAIRN_DEMO` | `false` | don't seed the `demo@cairn.local` account |
   | `TZ` ★ | e.g. `America/Denver` | container clock + calendar display; Render defaults to UTC |
   | `CAIRN_SITE_NAME` ★ | `Cairn` | shown in the header |
   | `CAIRN_DB` | `/data/cairn.db` | **Phase 1 only** — path on the mounted disk |

3. The blueprint also creates a 1 GB **persistent disk** mounted at `/data`.
   Disks require a paid instance type (`plan: starter` and up). On the free tier
   there are no disks — skip straight to the Postgres section, because without a
   disk **the SQLite file is wiped on every deploy and restart.**

If you'd rather not use a Blueprint: create a **Web Service** from the repo,
runtime **Docker**, health check path `/healthz`, add the env vars above, and add
a disk at `/data`.

## Phase 1 — SQLite on a disk

Nothing to do in code. Data lives at `/data/cairn.db` on the Render disk and
survives deploys and restarts. Back it up by downloading the disk contents from
the Render shell, or move to Postgres.

Limitations: one instance only (a disk can't be shared), no point-in-time
restore, and the disk is the single point of failure.

## Phase 2 — Postgres

The `postgres` branch teaches the store package both dialects. `store.Open()`
uses Postgres when the DSN is a `postgres://` URL and SQLite for a file path, so
setting `DATABASE_URL` is the only switch. Local dev and CI still use SQLite;
CI additionally runs the store suite against a real `postgres:16`.

Cutover, once `postgres` is merged:

1. Edit `render.yaml`: uncomment the `databases:` block and the `DATABASE_URL`
   env var, then **delete** the `disk:` block, the `CAIRN_DB` var, and (Phase 1
   only) `plan: starter` can drop back to `free` if you want. Push.
2. Render creates the `cairn-db` Postgres instance and injects `DATABASE_URL`.
   On boot the app runs `migrations/postgres/*.sql` against it.
3. **Move existing data** (skip if the disk is empty / you don't mind starting
   fresh):
   ```
   # get the SQLite file off the disk first — Render shell:
   #   cat /data/cairn.db | base64   (then decode locally), or use a one-off job
   go run ./cmd/pgimport -from ./cairn.db -to "postgres://…the DATABASE_URL…"
   ```
   It keeps ids, rebuilds the search index, and bumps the identity sequences.
   Sessions are not copied — everyone signs in again.
4. Redeploy. Verify sign-in, board, a search (`/search?q=…`), and the calendar.
5. Delete the disk once Postgres holds everything.

Render's **free** Postgres is deleted 30 days after creation — upgrade it (or
accept the reset) before then. Match its region to the web service's.

## Local development

```
go run .                       # http://localhost:8082 (or $PORT), SQLite at ./data/cairn.db
go test ./...
docker build -t cairn . && docker run --rm -p 8080:8080 \
  -e PORT=8080 -e CAIRN_DEMO=true -v "$PWD/data:/data" cairn
```

`CAIRN_DEMO=true` (the default) seeds `demo@cairn.local` / `demodemo` when the
database is empty.

Against Postgres locally:

```
docker compose up -d           # postgres on :5432, plus a cairn_test database
go run . --db "postgres://cairn:cairn@localhost:5432/cairn?sslmode=disable"
TEST_DATABASE_URL="postgres://cairn:cairn@localhost:5432/cairn_test?sslmode=disable" \
  go test ./internal/store/ -v
```

## Troubleshooting

- **Everyone logged out after a deploy** → `CAIRN_SECRET` is changing. Set it to
  a fixed value in Render (or let the blueprint's `generateValue` hold it), and
  make sure the database persists (a fresh DB regenerates the secret).
- **All data gone after a deploy** → no persistent disk (or not on Phase 2
  Postgres yet). This is expected on the free tier with SQLite.
- **Calendar times look wrong** → set `TZ`. Times are stored and shown in the
  server's zone.
- **Health check failing** → the app must bind `$PORT`; it does this
  automatically. Check the deploy logs for a migration error on startup.
- **`permission denied` writing `/data`** → the Dockerfile runs as root so the
  Render disk is writable; if you switched to `:nonroot`, revert or `chown` the
  disk.
